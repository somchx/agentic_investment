# Held-out dataset (`heldout-v1`) และ annotation protocol (ร่าง)

- **วัตถุประสงค์:** วัด A3 v2.2 เทียบกับ baseline บนชุดที่ไม่เคยใช้ออกแบบระบบ แทนการใช้ dev-v0.2 ซ้ำ
- **การใช้งาน:** ใช้ครั้งเดียวตามแผนที่ลงทะเบียนไว้ (`04_preregistration.md`)

## 1. องค์ประกอบ

| ประเภท | จำนวน | รูปแบบภายในที่ต้องครอบคลุม (โควตาขั้นต่ำ) |
|---|---|---|
| numerical | 30 | การเติบโต, margin, ระดับ ณ วันที่, การเทียบหลาย metric (≥ 3 ข้อแบบ "A + B > C"), การสร้างงวดเอง (Q4 / TTM) |
| ambiguous | 45 | คำประเมินที่ไม่มีเกณฑ์ (≥ 10), negative claim (≥ 8), scope ภูมิภาค / segment (≥ 8), คำประเมินที่รายงานให้เกณฑ์ไว้ (≥ 6) |
| interpretive | 45 | สาเหตุที่รายงานระบุชัด (≥ 12), สาเหตุที่รายงานไม่ระบุ (≥ 12), "primarily driven by" ที่ตัดสินด้วยสัดส่วนได้ (≥ 8) |

- **บริษัทและงวด:**
  - ใช้บริษัทที่**ไม่อยู่**ใน dev-v0.2 (AAPL, MSFT, AMZN, ADBE, INTC, PG, CAT) และไม่อยู่ใน Gold 150
  - ถ้าจำเป็นต้องใช้บริษัทเดิม ให้ใช้งวดที่ไม่ซ้ำ และติดป้ายไว้แยกวิเคราะห์
- **สัดส่วน label ที่คาด:** ไม่บังคับ แต่ต้องรายงาน **ห้ามคัด claim โดยดูผลของระบบ**

## 2. ผู้เขียน claim

- **เป็นคน ไม่ใช่ AI:** ชุด dev-v0.2 ร่างโดย AI และถูกระบุเป็นข้อจำกัดไปแล้ว
- **ผู้เขียนต้องไม่ใช่ผู้ติด label ของ claim ที่ตัวเองเขียน**
- **ห้ามดูก่อนเขียน:** ผลของระบบ, trace, error analysis และรายงานนี้ เฉพาะส่วนที่บอกว่า failure ไหน
  - ข้อจำกัดที่ยอมรับ: โควตาในข้อ 1 สะท้อน error ของ dev อยู่แล้ว
- **ผู้เขียนบันทึก:** แหล่ง SEC ที่ใช้และ pattern type ส่วน "คำตอบที่คาด" ให้แยกเก็บเป็น author-only และ**ห้ามใช้เป็น label**
- **ตรวจซ้ำ:** ใช้ `dev_claims_authoring.py validate` ตรวจความคล้ายกับ Gold, dev และกันเอง (เกณฑ์ ≤ 0.40) รวมถึงวันตัดหลักฐาน

## 3. การติด label

| ขั้น | ใคร | เงื่อนไข |
|---|---|---|
| Label คนที่ 1 | คน A | ใช้ workbook ว่างที่ผ่าน audit ความ blind และกรอกเวลาที่ใช้ทุกข้อ |
| Label คนที่ 2 | คน B ≠ A ≠ ผู้เขียน claim | ทำแยกกันพร้อมกัน ห้ามคุยกัน ห้ามใช้ AI ห้ามเปิดไฟล์อื่น |
| ตรวจตัวเลข | คน C (ข้อ numerical ทั้ง 30) | ใช้ checklist ตัวเลข นับเป็น label คนที่สองของข้อ numerical ได้ ถ้าไม่ใช่ A |
| คำนวณ κ | สคริปต์ | **ก่อน**ตัดสินข้อขัดแย้ง แยกตามประเภท |
| ตัดสิน (adjudication) | คน D ≠ ผู้ติด label ของข้อนั้น | ใช้แพ็กเกจ blind; **ควรมีผู้ตัดสิน 2 คนแบ่งงานกัน และให้ทั้งคู่ตัดสินร่วม ≥ 10 ข้อเพื่อวัดความสอดคล้อง** |
| อนุมัติ | ผู้วิจัย | `approve` + `validate`, ล็อกไฟล์ และบันทึก CHANGELOG |

**กติกาที่ได้จาก dev-v0.2:**
1. **ไฟล์ที่ส่งกลับต้องบันทึกจาก Excel:** มี document properties และไม่ได้เขียนด้วยสคริปต์ ไฟล์ที่ผิดกตินี้ต้องมีคำอธิบาย
2. **ต้องกรอกเวลาที่ใช้ต่อข้อ:** ถ้าเฉลี่ยต่ำกว่า 2 นาทีต่อ claim ให้ถามผู้ติด label ก่อนนำเข้า
3. **ตรวจความเป็นอิสระทุกไฟล์:**
   - ระบบตรวจข้อความซ้ำกับ AI และกับผู้ติด label คนอื่นอัตโนมัติ
   - ตรวจว่าหลักฐานซ้ำกับ AI ด้วย (รอบ dev พบว่าหลักฐานซ้ำ Codex แม้ label ไม่ซ้ำ)
4. **ห้ามมี "AI-generated adjudication":** การตัดสินทุกข้อต้องมี Declaration ว่าไม่ใช้ AI และ ID ของผู้ตัดสินต้องไม่ใช่ ID แบบโมเดล
5. **ห้ามมีไฟล์ที่ AI กรอกล่วงหน้าในโฟลเดอร์ที่ส่งให้ผู้ติด label เลย** (ไม่ทำ Codex comparison สำหรับชุดนี้)

## 4. ตรวจ provenance ก่อน freeze

ผู้วิจัยหรือผู้ตรวจที่เป็นคน ตรวจ label ทุกข้อว่า:
- มาจาก label สองคนที่ตรงกัน หรือจากการตัดสิน
- แหล่งทุกไฟล์มี hash, ผู้ทำ, วันที่ และ Declaration
- ไม่มีข้อใดที่ label เปลี่ยนหลังจากเห็นรีวิวของ AI ถ้ามี ต้องติดป้ายและส่งตัดสินใหม่

**รายงาน provenance ต้องอยู่ใน appendix ของเล่ม**

## 5. ลำดับและการ freeze

1. เขียน claim → ตรวจ → freeze ข้อความ claim (hash)
2. ติด label สองคน → κ → ตัดสิน → อนุมัติ → **freeze label (hash) ก่อนรันระบบใด ๆ**
3. รัน arm ตามแผนที่ลงทะเบียนไว้ และใช้ผลครั้งเดียว ห้ามปรับระบบแล้วรันซ้ำบนชุดนี้
